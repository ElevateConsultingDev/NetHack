# The improvement loop

Two loops improve the pilot. Both leave everything in git, so any step can be read, edited or reverted.

**Inner loop (the brain learns).** After every batch, `python3 -m pilot.reflect <run>` rewrites `pilot/memory/conclusions.md` (the brain's Stratigraph, see `pilot/memory/STRATIGRAPH.md`) from the games' records. HaikuBrain reads the journal at the start of every game. Humans can edit the journal at any time; the reflection keeps human lessons unless the records contradict them.

**Outer loop (the engine improves).** A Claude Code session runs one iteration per wake-up:

1. **Baseline.** Use the latest Haiku batch `playground/batch/<run>.json` as the baseline (run `python3 -m pilot.batch --games 16 --parallel 8 --brain haiku --seed 1000` if there is none since the last engine change). Always `--seed 1000`: baseline and candidate then play the same dungeons, which removes most of the game-to-game noise.
2. **Reflect.** `python3 -m pilot.reflect <run>`; commit the journal change on its own (`journal: <run>`).
3. **Pick one fix.** Take the largest failure bucket from the baseline. Choose the fix from, in order: the journal's "For the engine" section, `docs/pilot-plan.md`'s next undone item that targets that bucket, or the records themselves. One fix per iteration, smallest diff that does it. For a stall bucket, first look at the final maps of the stuck games (`playground/batch/<name>.json` has the state): iteration 13 guessed at search budgets and failed; looking at the maps showed 43 of 245 stalls were the pilot swallowed by a monster.
4. **Check.** `python3 -m pilot.test_prayer` and any other self-checks; replay the failed seeded games in that bucket (`python3 -m pilot.batch --replay <run>/<name>`: identical until the fix changes a decision, then shows what the fix did) and any saved scenarios (`python3 -m pilot.scenario list`, `run <name>`).
5. **Measure.** Decide on a deterministic pair: `--brain rules --seed 1000 --games 64 --parallel 16` without the change (stash it) and with it (one process per game since 2026-09-24: 64 games take about a minute; 16 dungeons overfit, see the held-out check). Compare with `python3 -m pilot.compare <without> <with>`. Rules plus a seed repeats exactly, so every game that differs differs because of the change (games with identical keys confirm it), and it takes about a minute. Then run the 16-game Haiku batch with `--seed 1000` for the journal and as the next baseline; live Haiku answers vary run to run, so its bucket counts are too noisy to decide on (iteration 3: Haiku said melee 6 -> 8 while every targeted game improved; the rules pair showed the change was really worse).
6. **Keep or drop.** The goal is to ascend, so progress is judged by depth first (Dave, 2026-09-24). Keep (commit with the before and after numbers, then push) if the average deepest level rose by 0.25 or more and average XL did not fall by more than 0.25, or if the target bucket shrank and the average deepest level did not fall. Otherwise drop the engine change (`git checkout -- pilot/engine.py` and whatever else changed), and add a note to the journal's engine section saying what was tried and what happened.
7. **Every third iteration, two checks** (log the result under "Check log" below):
   - **Journal A/B.** `--brain haiku --seed 3000 --games 32`, once as is and once with `--no-journal`. Haiku varies run to run, so this uses 32 games and its own seeds. If the journal arm isn't ahead on average deepest level, the journal isn't earning its place: cut it back to the lessons the records clearly support (or to the last version that tested ahead) and note it in the journal's intro.
   - **Held-out seeds.** `--brain rules --seed 5000 --games 64 --parallel 16`, compared with the previous held-out run. Keep or drop never looks at these seeds, so they show whether gains made on seed 1000 carry over to dungeons the loop hasn't tuned for. If seed 1000 improved and 5000 didn't, say so in the report.
8. **Record.** Mark finished plan items done in `docs/pilot-plan.md` with the batch numbers. The new batch is the next baseline.

Guardrails: work on the `ai-player` branch only; after each kept fix, push `ai-player` to the `elevate` remote (ElevateConsultingDev/NetHack; Dave, 2026-09-24), never anything else; never edit hooks or settings; hard safety rules stay in the engine, never in the journal alone. 16 games is noisy: a change that only moves one or two games is not evidence.

## Stratigraph efficacy (what Dave wants validated)

The question is not "does the brain help" but "does the brain get better as strata accumulate". Protocol (`python3 -m pilot.strat`): a fixed **test set** (seed 3000) the reflection never sees; **training batches** on fresh seeds (4000, 4100, ...), each followed by `pilot.reflect` (a new stratum); after every stratum, a test batch with that stratum's conclusions, compared with the no-conclusions test arm, paired by seed with its margin of error. The result is a learning curve: depth on the test set as a function of strata. A flat curve means the reflection is not learning anything that transfers; a rising one is the Stratigraph working. 32 games per batch gives a margin of about 0.35 levels; 64 halves the time to a verdict per unit of confidence. Run it on Qwen 3 8B first (free, local), then Haiku.
